# 独权收窄的实证迭代闭环（P06-4/P06-5 蒸馏，2026-09-27）

> 来源：P06-4（基于运行上下文隔离与重试归并的电力垂类模型考试评测方法）与
> P06-5（一种基于题目版本依赖的派生评测数据失效与局部重算方法）两案在
> incoPat 停机期间完成的一整轮"现有技术核验 → 独权收窄 → 量化验证 → 论据补强
> → 多角色评分"闭环。核心纪律：**任何"应该更好"的改动都要用量化门禁实测，
> 不达预期就回退，不凭直觉判断"这次肯定有用"。**

## 零、何时启用本闭环

- 已有一版可用的申请文件（权利要求书+说明书+附图+摘要齐全），且已跑过至少
  一轮浏览器四端评审或人工复核，进入"精修"阶段；
- 委员会/评审角色（`patent-grant-scorer` 四角色或浏览器四端）反复提出"独权
  含非必要特征""独权过长"这类结构性意见，但团队此前只做过排版式整理；
- incoPat 等法定检索不可用，需要免费渠道先把证据缺口降到最低。

## 一、现有技术核验（incoPat 不可用时）

1. 团队已知/四端评审已提及的候选，逐件用 Google Patents WebFetch 直连取
   著录项+独权1原文（`https://patents.google.com/patent/<PN>/zh`），比
   `google-patents-search` 的 `patentscope` 后端更稳（无需处理字段/编码问题）。
2. 用 `google-patents-search` 的 `gp_search.py`（`FP` 字段，非 `EN_ALLTXT`——
   见该 skill 2026-09-26 的 bug 修复记录）跑 3-6 组 2-3 词概念检索式做增量
   关键词召回；有已知种子件时用 `gp_pipeline.py --seed` 或
   `gp_bigquery.py similar`（需 GCP 沙盒，见 `gcp_bigquery_setup.md`）补语义轴。
3. 每件候选写一份 `paa/evidence/prior_art_claims/<PN>.md`（著录项+独权1原文+
   逐"核心区别节点"映射表+清洗结论），检索过程写一份
   `paa/evidence/prior_art_search/<渠道>_<日期>_<案号>.md`（如实记录每轮检索式、
   命中数、方法论边界），最终汇总成正式的 `01_现有技术检索报告.md`
   （按 `templates/01_现有技术检索报告_template.md` 六段式）。
4. **硬性边界**：免费渠道不判断抵触申请、不判断法律状态、不是系统性穷尽检索
   （只核验已知候选+有限轮次扩检）——这些必须在报告"结论与边界"里如实声明，
   incoPat 恢复后仍需补一次正式检索。

## 二、独权收窄——先温和，后激进，中间必须实测

### 第一步：温和收窄（去重复，不改保护范围）

1. 逐条比对独权1与各从权文字，找出**逐字或近乎逐字重复**的具体判据段落
   （常见于：原子条件更新的具体条件枚举、多重一致性校验的具体规则、并发
   控制的具体重试/接管步骤）；
2. 把独权1里的重复段落改写为**抽象引述**（如"满足预定的XX条件"），具体判据
   完整保留在对应从权里一字不改；
3. **逐条核查每一个从权**（不只是被动新增，是全部从权）：确认它依赖的每一个
   前提术语在收窄后的独权1里是否还存在——这是最容易出错的一步，本轮在
   P06-5 排查中发现过"若整句删除会导致某从权悬空引用"的真实风险（该从权
   依赖独权1而非另一条定义了同一术语的从权，不能想当然借用）；
4. 用 `terminology-keeper`（或等价扫描）跑一遍四份正式文件，**这一步真的抓到
   过范围风险**：P06-4 曾误删一句非重复性的独权限定（导致独权实际变宽），
   被扫描发现后原样恢复；
5. 用 Jev 门禁（见 `docs/P06评审流程优化_Jev接入_20260925.md`）复测清楚性
   风险/因果链闭合分——**建立收窄前后的对照表，不要只看单次结果**。

### 第二步：激进收窄（真正移出独权，仅在有委员会建议且温和收窄验证过量化基线后再做）

1. 委员会角色（尤其 attorney/invalidator）若明确建议"把某整段机制移出独权
   只留从权"，先判断该机制是否已被某条从权**完整独立承载**（不依赖独权1
   重复提供定义）——若是，删除风险低；若否，先把它补成从权再删独权对应段；
2. 同上做从权前提术语核查（这一步比温和收窄更容易出问题，因为整段删除比
   局部抽象化更可能带出隐藏依赖）；
3. 同步改写说明书里对应的"与现有技术的区别"论证：把"N项特征需要同时成立"
   降级为"独权核心M项 + 从权在此基础上的优选补强"两层论证；
4. **改完必须重新跑 Jev 门禁比对**，不能假设"更精简=分数更好"。本轮两案给
   出了相反的证据：P06-4 中性（分数几乎不变），P06-5 明显变差（因果链闭合
   与清楚性风险双双恶化）——移出的机制若是因果链里承担"输出约束"角色的
   环节（如并发/崩溃恢复），删除后独权在该处变成空转门禁，量化门禁能测出
   这一点，人工审阅未必能。
5. **数据不支持就回退，不要因为"已经做完了"而将就**：用
   `git checkout <收窄前commit> -- <受影响文件>` 精确回退到量化基线，
   重新跑 Jev 确认恢复，采纳记录**不删除**、只加"已撤回"标注保留决策历史
   （为什么试过、为什么放弃，本身是有价值的存档）。

## 三、论据补强（不改权利要求，只改说明书论证——随时可做，独立于收窄决策）

对说明书算法章的每一处公式/判据，按"技术绑定+技术效果"框架
（见 `knowledge/常见问题与避坑.md` 客体审查一节）分类：

- **公知实现细节**（如指数退避公式、布尔判据的具体运算）：补一句明确声明
  "本节给出定义式仅满足26.3参数依据要求，不主张该判据本身构成区别特征，
  区别在于XX（指回真正的核心判据/联动结构）"——防止审查员或无效请求人把
  这类细节当靶子攻击时，显得申请人自己曾主张其为创造性来源；
- **真正的技术效果论据**（如身份差集校验、覆盖关系判定这类"纯数量/纯时间戳
  会漏判但本方法的比对方式不会"）：检查是否已有"取消该限定会怎样"的反例
  推演——若只有功能描述没有对比论证，仿照已有反例段落的格式补一条具体
  失效场景（设两个并发请求/两次操作，说明简单方案在什么条件下给出错误
  结果），为 OA 答辩"第二作用"模板（见 `oa-response-playbook.md`）预埋弹药。

**预期管理**：这类补强不会移动 Jev 的清楚性/公式自洽分数（那两项测的是
文本本身的技术表述质量，不是论证说服力）——补强的价值在收到真实 OA 时
才兑现，跑 Jev 复测只是确认"没有意外破坏什么"，不要指望它验证补强是否
有效。

## 四、多角色量化评分（跟踪趋势，不是一次性打分）

- 用 `patent-grant-scorer` 的四角色评分（`scripts/_review_batch/score_case.py`
  是本仓自建的轻量版：CLOUBIC 走 examiner=deepseek 系顶配 pro 档、
  attorney=GLM 系顶配、analyst=Qwen 系"代号最新"档；MINIMAX 走
  invalidator=MiniMax 系最高编号）；
- 每次账号可用时先探测模型目录（`/v1/models`）确认"顶配"三个字具体对应
  哪个型号——模型命名混杂"版本号大小"与"档位高低"（如 pro/flash、
  max/plus）两个独立维度，二者不总是同向，遇到歧义找人确认，不要自己猜；
- Windows 上 `urllib`/`ssl` 默认证书链可能验证失败，设
  `SSL_CERT_FILE=$(python -c "import certifi; print(certifi.where())")`
  而不是关闭证书校验；
- invalidator 角色的分数天然偏低（其设定就是最严苛的攻击视角），单看它的
  总分没有意义，要看它提的具体 p0/p1 意见是否已被其他三角色的高分佐证为
  "已充分论证但仍值得警惕"还是"确实是硬伤"；
- 把新旧两轮评分并排比较增量，而不是只看单轮绝对分——四个模型本身也在
  迭代（版本号、量化范围都可能变），绝对分跨轮次不完全可比，趋势比绝对值
  更可信。

## 五、全程留痕（每一步都要能倒查"为什么"）

- 每次实质性改动升版本号（内部批次号，非日期），配一份"采纳记录"文档
  （改了什么、为什么安全、对从权的前提术语核查表、Jev 复测对照表）；
- git commit message 里写清楚"为什么"而不只是"改了什么"；被撤回的改动
  不删除记录，只加撤回说明，保留决策历史供以后同类判断参考；
- 免费渠道核验、独权收窄草案、正式采纳、Jev 复测、四角色评分——每一类
  产物固定放在同一案件目录下的固定子路径，方便下一轮迭代或下一个案子
  复用同一套目录约定。
