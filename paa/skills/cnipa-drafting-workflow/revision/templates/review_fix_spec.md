# v<X> 修订规范模板：按外部评审意见修改（review_fix）

> 用法：复制到批次目录为 `00_v<X>修订规范.md`，填 `<>` 处；每案一个子代理。项目根 `$P`，批次 `$B`。先读本规范、`$P/CLAUDE.md`、`$P/knowledge/撰写速查卡.md`、各案上一版修订说明。

## 0. 输入与证据层级

- 评审原文：`<案>/paa/evidence/browser_review/*.md` 或代理人意见文件；注明哪些是本轮、哪些是旧轮。
- 评分口径：每个评审端写明"1 低风险 9 高风险"还是"越高越好"；偏放行的评审只作对照，不作放行依据。
- 评审结论是模型 / 人的意见（judge 级）。**每条意见先对照 02/03/04/05 原文核实**；成立才改，不成立或不宜改的在修订说明里写"不采纳"及理由。评审里出现的公开号 / DOI 一律先核验（第 1 节）再使用。

## 1. 先核验新对比文件

- 专利：`gp_fetch.py --backend tavily <公开号...> --out <案>/evidence/prior_art`（间隔 ≥2 s），拟引用 JSON 跑 `gp_verify.py --citations <案>/evidence/citations_v<X>.json --docs <案>/evidence/prior_art`。
- DOI / arXiv：Crossref `https://api.crossref.org/works/<DOI>`、arXiv `https://export.arxiv.org/api/query?id_list=<id>`。
- 通过的写入 `01_现有技术检索报告.md`，注明来源（"网页模型评审线索，relay 取件核验"），按真实内容定 X/Y/A，不照搬评审等级；取不到的列入 01"未核验线索"并写失败原因。发现 X 类立即停下回报主代理。
- 若属抵触申请排查：核对申请日 / 公开日与本案申请日的先后，写明是现有技术还是抵触申请。

## 2. 修改原则

1. 先补执行逻辑和清楚性缺口（第 26 条第 3、4 款，细则第 20/22/23 条），再按多数评审的退守组合把从权并入权 1 强化创造性。并入时保持"机制展开式"：写场景约束 → 机制，不把公式搬进独权。
2. 第 33 条意识：未递交的案允许补入新机制，但必须写进具体实施方式，并在修订说明里标"新增技术内容（申请前补入）"；已递交的案只能在原记载范围内改。
3. 权利要求禁"约/大概/左右"；阈值写取法与关系，不写固定数；效果用"计算例（合成/仿真数据，非实测）"口径；禁"100%/大幅/领先/显著"。
4. 02–05 不写来源领域术语、脚本文件名、版本标记、"评审 / GPT / 模型"字样。
5. 改了计算例相关的条件，用现有脚本复跑受影响的计算例，新随机种子，数字如实更新；不利结果如实写并收窄主张。
6. 术语与附图标号全文一致；权项编号变动后同步说明书引用、04 流程图、05 摘要、06/07、paa。
7. 独权 1 项 + 系统 + 介质 + 设备，从权 10–15 项为宜。

## 4. 产物与校验

- 工作文件 00–07、`_drafting_outline.md`、`paa/` 同步；`validate.py <案>/paa` 四门禁 PASS（检索门禁如实）。
- 07 末尾追加本轮评审记录：各端风险分（注明口径）、采纳 / 不采纳条数、本版响应。
- 快照 `申请书_v<X>/`（00–07、大纲、附图、查新小结）+ `修订说明_v<X-1>_to_v<X>.md`：逐条"评审意见（端 / 位置）→ 核实结论 → 改了什么（权项号 / 段落号）→ 依据"，不采纳项单列，新增技术内容清单，从权编号映射。
- AHP 重评：更新 `evidence/scoring/scoring_input.json`（claim_hash = sha256(02 字节)、search_input、证据绑定、四角色打分如实），`ahp_only_scorer.py evidence/scoring/scoring_input.json -o evidence/scoring/scoring_result_v<X>.json --root $P`，非 stale；复制为 `scoring_result.json`。
- 不做：Word（主代理统一出）、git 提交、改别案、改技能库、浏览器、BigQuery、metaRSI 写入；重启脚本只杀自己的 PID，禁止按进程名终止。
