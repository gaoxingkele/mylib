# 充分公开与支持

本参考用于区分并检查两个常被混淆的问题：

- **充分公开：**说明书是否清楚、完整，使本领域技术人员能够实现该发明；
- **权利要求支持与清楚：**权利要求的概括范围是否能够从说明书公开内容中得到，边界是否可确定。

语言写得流畅不等于已经充分公开，实施例很多也不当然支持任意宽的概括。

## 一、充分公开检查矩阵

对每个独立权利要求的核心技术特征检查：

| 维度 | 最低公开要求 |
|---|---|
| 术语 | 含义明确，与本领域通常含义不一致时给出定义 |
| 输入 | 来源、格式、单位、采样或获取条件 |
| 处理 | 步骤顺序、模块关系、计算或控制逻辑 |
| 输出 | 内容、去向及如何被后续步骤或设备使用 |
| 参数 | 范围、单位、测定条件和确定方法 |
| 边界 | 适用条件、终止条件及不适用情形 |
| 异常 | 缺失、冲突、超时、越界和故障处理 |
| 效果 | 与技术手段的因果关系及必要证据 |
| 实施例 | 至少一种可执行路径，覆盖核心创新机制 |

如果本领域技术人员仍需进行创造性劳动、反复试错或补出关键步骤才能实现，通常存在充分公开风险。

## 二、AI、模型和算法方案

根据自 2026 年 1 月 1 日起施行的《专利审查指南》修改，按方案性质补充以下内容：

### 涉及模型构建或训练

- 对发明作出贡献的模型模块、层级或连接关系；
- 训练数据的构成、处理方式和与任务的关系；
- 具体训练步骤、损失或约束、参数更新方式；
- 对实现效果必要的关键参数及确定方式。

### 涉及具体领域应用

- 输入、输出数据分别对应什么技术对象或状态；
- 算法处理与具体场景之间如何结合；
- 输入与输出之间对实现技术效果有何内在关联；
- 输出如何参与检测、控制、资源调度或其他技术过程。

仅披露模型名称、通用框架或“调用模型得到结果”，而关键连接和处理机制又不是公知常识时，存在明显风险。

## 三、效果与实验数据

- 能由技术原理直接推导的效果，应说明推导链条。
- 必须依赖实验才能确认的效果，应给出实验方法、条件、评价指标和足以说明效果的结果。
- 对比实验应尽量只改变待证明的关键因素，并说明基线与样本条件。
- 不得编造实验数据；没有数据时，应收窄结论、补做验证或明确列为待补事实。

## 四、权利要求支持检查

把每个权利要求特征映射到原始申请文件的具体段落、附图或实施例：

- **强支持：**原文直接记载该特征、关系和效果；
- **可论证支持：**本领域技术人员可从原文直接、无歧义地得出；
- **弱支持：**只有目标或效果，没有实现手段；
- **无支持：**原文不存在，或需要组合互不关联的实施例才能得到。

独立权利要求的核心限定不得停留在“弱支持”或“无支持”。概括到上位概念时，应检查说明书是否给出足够代表性实施方式，以及同类替换是否都能解决同一问题并取得相应效果。

## 五、修改不得超范围

申请后修改应以原说明书和权利要求书记载的范围为限。以下做法风险较高：

- 为避开对比文件新增原文没有的参数、步骤或连接关系；
- 从附图尺寸推导原文未明确公开的精确比例；
- 把多个彼此独立的实施例特征任意拼成新组合；
- 把“可选”或特定场景特征改写成普遍必然关系；
- 用后补实验首次证明原申请未能使人确信的核心技术效果。

## 六、放行条件

提交前至少满足：

- [ ] 每项核心特征均有实现方式，而非仅有功能名称。
- [ ] 技术问题、手段、机理和效果能够逐项对应。
- [ ] 关键参数、公式、变量和边界条件可执行。
- [ ] AI/算法方案公开了与创新贡献相称的结构、训练或领域关联。
- [ ] 权利要求范围与说明书贡献相称，并有逐项依据。
- [ ] 所有补充内容均来自真实技术事实，且申请后修改不超出原始公开。
