# metaRSI：设计来源与 v0 的取舍

2026-10-04。v0 是用户给出的「MetaCog-RSI 完整技术设计」的一个缩减实现。这里记原方案是什么、v0 实现了哪些、改了哪些、哪些没做，以及原因。原方案全文没有存进本目录。

## 原方案（摘要）

- 六层：L0 不可变内核（宪法、真理度量、验证层级、安全不变量）；L1 元认知总控（能力边界建模、验证器选择、策略调度、信息增益评估）；L2 执行循环（计划、执行、验证、归因、筛选）；L3 记忆（经验图谱、情景/语义/程序/策略/负面记忆）；L4 工具与环境；L5 运行时网关（准入控制、回滚、预算、审计）。
- 存储：PostgreSQL + pgvector、Neo4j、Redis、MinIO；十组表（任务、Episode、ThoughtTrace、五类记忆、经验图谱、InsightCard、验证与准入、版本、评估器状态、Benchmark）。
- 接口：REST、WebSocket 事件流、Python SDK。
- 六个补丁：验证层级选择器；安全硬约束（可验证性、方向控制、回滚）；能力边界建模；四更新表面；信息增益 = 新颖性 × 相关性 × 可操作性；Benchmark 饱和与动态难度。
- 五个阶段：记录与回放 → 实验闭环 → 外部探索 → 元认知与 RSI → 安全与 UI。

原方案列出的依据：RSI Survey 2026（Chen et al., arXiv:2607.07663）、Alibaba RSI Survey 2026（Liu et al.）、Gödel Agent（Yin et al., ACL 2025）、Self-Healing Harness（Tayebati et al., 2026）、Self-Verification Cliff（Jain, ICML 2026）、Trellis / Experience Graphs（Liao et al., 2026）、MAGELLAN（ICML 2025）、MUSE（2025）、ModularRSI（Wu et al., 2026）。**这些文献由原方案给出，写 v0 时没有逐篇核对原文**；其中引用的数字（例如 55% 的候选修改在修好触发问题的同时损坏了受保护行为）同样未核对。

## v0 实现了什么

| 原方案 | v0 | 位置 |
|---|---|---|
| L0 宪法、安全不变量 | 项目内 `constitution.json`：受保护面、每个面需要的最低证据等级、是否需要人批准 | 由人编辑，工具初始化后不再写 |
| 验证层级选择器 | 证据等级由「在哪选定、在哪计分、这类问题在该窗口上用过几次」算出 | `Project.tier_of` |
| 准入控制（生成与持久化分离） | `propose` 只能得到 `rejected` 或 `pending_human`；`decide` 必须带人名 | `cmd_propose` / `cmd_decide` |
| 回归检查（受保护行为） | `propose --check 名称=pass|fail`，有失败项直接拒绝 | 同上 |
| 负面记忆 | `negatives` 表、`wiki/negatives.md`、`search` | |
| Episode / 审计日志 | SQLite 的 `events` 表只追加、逐条哈希相连；`episodes` 等查询表由它重建 | `verify-ledger` |
| 经验图谱（一等数据库状态） | `wiki/graph.md`：窗口 → 问题类别 → 试验 → 否决项的 mermaid 图，由数据库生成 | `render_wiki` |
| 能力边界建模 | `calibration`：弱等级上显著的结果，到更强等级还成立的比例。用账本里的实测替代自报置信度 | `cmd_calibration` |
| 元认知状态与模式切换（explore / exploit / verify / reflect、fatigue） | `tick`：后台学习或进化，进化分验证、留出、登记影子三个阶段；疲劳按「某类问题最近 3 条试验都没通过」计 | `decide_mode` |
| 运行时的 Detect → Notice | `signal log` 和脚本里的 `emit_signal`：用户请求、故障、漂移 | `cmd_signal` |
| 四更新表面里的「行为 / 策略」更新，以及 Self-Healing 的回归检查 | 模型登记与模型审计：评估与上线是否同一个模型、各次训练是否同一类、拟合窗口、样本外区块、外推损失、增益是否落在全市场同值特征上、选股画像 | `model_flags`、`cmd_model` |
| 预算 | 评估数据当作会被用掉的预算：窗口状态 `open / consumed / reserved`，以及每个窗口上比较过的规则数 | `windows` 表、`status` |

## 改了什么，为什么

1. **数据库换成项目内的 SQLite 加 LLM wiki 风格的 Markdown（用户 2026-10-04 定）。** 原方案要起四个服务。单人、单机、每天几十条记录的规模用不上。SQLite 是一个文件，能写 SQL；Markdown 页面由数据库生成，人和代理直接读，也让 git diff 看得见每次写入改了什么。两者都放在使用 metaRSI 的项目目录里，mylib 只留代码和默认配置。表名和原方案对得上（episodes、trials 对应 verifications、admissions 对应 admission_records、negatives 对应 negative_memory），以后要迁到 PostgreSQL 是一次性导入。v0 的第一版用过 JSONL，同一天改掉。
2. **验证层级不按任务类型查表，按证据来源计算。** 原方案是 `code_correctness → formal`、`open_research → external_judge` 这样的静态映射。实证研究里同一类任务的证据强弱差别很大：同一条规则，在看出它的那段数据上 t 值是 5，换一段没看过的数据是 0.1。所以等级取决于规则在哪选、在哪验、那段数据为同类问题用过几次。
3. **加了原方案没有的一层：评估数据是消耗品。** 留出窗口用一次就不再是留出；在同一窗口上比较的规则越多，单条规则需要的显著性越高。v0 记录窗口状态和累计比较数，并给出 Bonferroni 折算后的门槛。保留窗口只能用来给事先登记的影子规则计分。
4. **`judge` 级证据不能准入。** 原方案对最弱一级的处理是 `max_improvement_rate=0.1` 加人工审查，这个比率没有定义对象。v0 的规则更直接：模型或评审的意见不构成改动受保护面的证据。
5. **什么时候进化，由账本和日历决定。** 原方案的 `should_switch_strategy` 看 `fatigue` 和模型自报的 `confidence`。v0 的规则是：进化要同时有理由和验证途径，缺一样就只在后台学习。理由是到期的影子规则、用户请求、或累积到阈值的故障与漂移；验证途径是未用过的留出窗口、或保留窗口加影子登记。这条规则把「自改进强度跟随验证层级」落成了开关：没有比已用数据更强的验证手段时，系统不启动改进，只积累记录。
6. **用实测校准替代自报的置信度和能力估计。** 原方案的 `MetacognitiveState` 里 `confidence`、`competence_estimate` 是模型自己给的数。v0 不存这些，改为从账本里统计「弱证据到强证据的保持率」。
7. **第四阶段的验收标准改了。** 原文是「无人类干预下完成 3 轮以上改进循环」，这和 L0「改变优化目标必须人批」冲突。v0 的口径是：循环可以自动跑，但落到受保护面的每一次改动都必须有人批准的准入记录。
8. **评估器自身的更新归入受保护面。** 改评分口径等于改优化目标，按方向控制处理：把定义指标的文件列进 `protected`。
9. **不记 ThoughtTrace。** 逐条记录思考成本高、回看价值低。v0 记到 Episode 一级：问了什么、答了什么、依据哪些试验、留下什么。

## 2026-10-05 的升级：从管规则到管模型

v0 的证据等级管的是「一条规则在哪段数据上验过」。在第一个项目里用了两天，暴露出它管不到的一类问题：滚动验证各折的模型和最后上线的模型不是同一个东西（同一份脚本，早停在不同窗口停在 1 棵树和 247 棵树；上线模型的排序部分只用两个月数据拟合），于是开发期的全部证据描述的是另外几个模型。按证据等级看这些证据是合格的，实际上不能用。

升级的思路是把「模型能不能外推」拆成几件量得出来的事，由项目登记、工具按固定规则判断：

- **同一性**：评估用的分数是不是这个模型自己打的。
- **结构稳定**：同一做法各次训练出来的模型大小是否相近。
- **数据够不够**：拟合窗口多长。
- **样本外够不够**：有几个它没见过的区块，过半为正没有。
- **外推损失**：见过的窗口和没见过的窗口差多少。
- **学的是什么**：增益是不是大半落在全市场同值的特征上。
- **选了什么**：名单和全市场差多远。

审计之外还有一步 `model diagnose`，回答「下一步往哪用力」：把各模型自己打分的样本外区块摆在一起，做法不同的模型在同一批区块一起失效，原因在模型之外，该去管仓位和风控；各自在不同区块失效，说明它们互补，该验证的是组合或按行情切换。第一个项目上的结果是后一种。

这些检查不提高模型本身，它们防的是把不能外推的模型当成能外推的。提高外推能力靠的是训练规程（写死做法、区块全在训练之后、特征去量纲、按日排序），规程写在调用手册里，执行仍在项目脚本。

没有做的：由工具自动发起重训；自动比较多个候选模型并选优；留一段行情不训练来专门测外推（leave-one-period-out）。前两件会把选择权交给在已用数据上的比较，和证据等级的原则冲突；第三件值得做，但要项目脚本支持。

## 没有实现

- 信息增益评分与 InsightCard、外部检索（Meta-Teacher）。三个因子都是模型自评，相乘之后的数只适合给阅读队列排序，v0 不提供。
- 图数据库和向量检索。`graph.md` 只是把证据关系画出来，不能做图查询；`search` 是关键词匹配。
- 策略记忆、程序记忆、策略调度、Benchmark 适配器与动态难度。
- REST / WebSocket / Web 控制台、Docker 沙箱、自动回滚。回滚依赖 git。
- 运行时拦截和常驻进程。v0 只在被调用时检查。`tick` 可以由 Claude Code 的 SessionStart / UserPromptSubmit 钩子自动触发（`hook` 子命令），其他宿主靠代理每回合调用；钩子只负责把模式告诉代理，不拦截工具调用。

## 什么时候值得往原方案的方向扩

- 账本超过几千条、关键词检索找不到已有结论时，再上向量检索。
- 多个代理并发写同一个项目时，再换数据库。
- 有了能自动判分的 Benchmark（代码类任务）时，再做执行循环和策略记忆；研究类项目的瓶颈在证据纪律，不在循环速度。
