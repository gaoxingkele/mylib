### Hook 到驾驶舱

1. 在工具支持的生命周期点捕获有用结果，例如验证结束、明显阻塞、本轮结论；各工具按实际版本验证。对暂缺 Hook 的工具，先支持主动上报和可授权的启动器适配。Hook 局部脱敏，只将有界摘要和证据引用写入本机队列。保留工具与版本、项目、会话、轮次、步骤 ID、来源证据级别及使用的 mylib 技能版本。
2. `report_step` 由后台进程调用。服务器根据凭据映射项目和工具身份，在同一事务写入事件、幂等回执和额度待查任务。提交成功后返回 `event_id` 和服务端序号。相同 ID 和内容的重试使用原回执；内容不同则报冲突。网络不可用时由本机队列补交。
3. **每条已入库 Hook 事件都触发对应计费账号的查询。** 查本周余量和下次周重置，并经 `record_usage_snapshot` 写回，关联原事件。相同账号已入库的并发事件可共用一次新查询。限流或登录过期作为结果状态写回，再按厂商限制重试。较早的查询结果可入历史，当前值取最新有效快照。每条快照保留厂商原单位、周期、来源、UTC 查询及重置时间，未知字段为空。登录凭据留在运行采集器的机器，订阅共享额度按池去重。
4. `search_task_events`、`get_task_status`、`get_usage_overview` 供右侧驾驶舱及总管使用。查询按项目授权和账号权限过滤，可按事件 ID 回查证据。新增写入权限仅限对应项目和计费账号。总管在本地任务完成后可用现有 mylib MCP 检索，并将有证据的可共享经验提交为候选信号。

### 项目 wiki 与中央数据库同步

保留开发端现有的 wiki 写入入口。每次值得沉淀的步骤生成一份可分享的决策记录，两处使用同一份正文。正文写清任务目标、结论、关键依据、考虑过的方案与取舍、验证结果、适用边界和待办。通过证据链接关联测试、提交或原记录。采集字段限于作者或工具明确输出的决策说明。

1. **本地落地。** Hook 为记录分配稳定的 `entry_id`，关联 `task_id`、`attempt_id`、`event_id`、版次和前一版标识。先将待写的正文及内容摘要持久保存，再由现有 wiki 写入器按记录 ID 写入项目页面，成功后进入待同步状态。重启时重放未完成项，同一记录只出现一次。项目若使用 metaRSI 的生成式 wiki，则经原生账本写入接口生成页面，读取其稳定记录作为同步来源。 [metaRSI 的 wiki 写入规则](../../skills/meta-rsi/SKILL.md)
2. **中央入库。** `report_step` 可随步骤携带已落地的决策记录版本。服务在同一事务中保存任务事件、可分享正文、项目内相对路径和锚点、版本摘要及关联关系，提交后返回回执。客户端按回执确认该版本已同步。断网期间可读本地 wiki；按版本补传，同 ID 同版同内容的重试返回原回执。纯文档修订关联原步骤，避免额外触发额度查询。
3. **修订与交叉验证。** 更正通过新版引用旧版，保留证据和修订历史。两台机器对同一父版同时提交不同修改时保留分支并提示待核对；不同验证者用独立记录表达各自结论。撤回或共享范围变化时，中央查询、索引和缓存同步更新。审批通过的通用经验才进入 mylib 的版本发布流程。
4. **驾驶舱读取。** 按当前用户权限聚合同一任务的记录，展示结论、依据、来源机器与工具、验证版本和同步时间。用户点开引用可直接读取中央信任范围内的对应版正文；源机在线时还能定位项目 wiki 页面。未知或延迟的来源标注最近同步时间。模型回答按需要检索相关条目，保留分歧与证据引用。

验收场景：A 机断网完成步骤并写入 wiki，恢复时因回执丢失重复上报；B 机随后给出相反验证结论。验收本地记录可读，中央仅有一份 A 的该版本，B 的结论独立可见，驾驶舱能从两份结论分别回查原文、代码版本和验证证据。

### 同一任务的接力与并行交叉验证

驾驶舱按任务聚合。首次创建任务时分配 `task_id`，后续在现有任务上选择「接手继续」或「加入验证」。目标电脑可用任务链接或 ID 绑定本地会话。Hook 上报时携带服务端确认的 `task_id` 和本次 `attempt_id`，窗口标题只用于展示。同一台电脑从 Codex 切换到 Claude Code 与跨电脑接手使用同一流程。

| 操作 | 需要记录的内容 | 驾驶舱行为 |
| --- | --- | --- |
| 接手继续 | 前次执行、交接原因、当前目标、已完成项和待办、最近验证结果，以及可获取的提交或补丁引用 | 新执行成为当前主执行。旧执行补传的事件仍归旧执行。遇到额度不足时显示原账号及重置时间；新账号的事件和额度快照独立关联。原账号额度恢复后即可再选用，接手关系由显式操作决定。 |
| 加入验证 | 验证目标、指定的代码提交或工件摘要、验收条件、验证工具和证据；必要时记录平台差异 | 当前主执行继续工作，多个验证者同时上报，各自保留结论。界面显示完成数和待返回数；同一版本结论冲突时标记「待裁决」，基线不同时标记「待对齐版本」。 |

跨机交接时，接手方确认能读取对应工件。若关键改动只在上一台机器的工作区，先标明「待同步改动」，由原端提供可访问的补丁或提交。多工具需要同时修改同一仓库时，各自记录工作树、基线和产出，交付或合并结果另记事件。

交接与登记新主执行放在同一事务，并检查预期的前次执行 ID。两台机器同时接手时，后一请求能看到当前负责人并重新选择。单个执行完成只更新该执行结果；任务需要交叉验证时，依据预先记录的必要验证项和裁决结果结案。额度暂停、断线和验证未返回各有独立状态。

### 驾驶舱中的 mylib、RSI 与窗口回馈

**桌面端 mylib 目录。** 首次使用时，Windows 桌面端在运行该界面的电脑上读取 `D:\aicoding\mylib`。在「驾驶舱 → mylib → 目录设置」显示电脑名与当前绝对路径，可选择其他本机文件夹，也可恢复默认。优先读取该桌面端已保存的本机目录偏好；验证新目录存在且可读后，保存到本机并重建本地索引。验证失败保留上一次有效设置。切换项目、房间或远程窗口继续使用这份桌面设置。中央 MCP 的发布快照与目标 Agent 实际加载的版本分别标注来源。

验收示例：在桌面电脑 A 选择自定义目录，切换到电脑 B 的终端并重开驾驶舱，仍显示 A 的自定义路径；重启 A 后设置保留。电脑 B 自己打开桌面端时读取 B 的偏好。Android 继续通过已授权来源浏览技能。 [现有本机偏好与索引](/D:/aicoding/supermonoagent/.omx/worktrees/conversation-journal/src/supermonoagent/desktop_assistant.py:19)

驾驶舱提供常驻的「mylib」入口，可从总管对话直接进入。默认显示适合当前任务的 skill 和 harness，以及当前执行实际使用的版本。「进化记录」在 mylib 内展开，集中呈现候选改动、评测差异、已发布版本、适用工具和已采用的窗口。普通 Hook 上报和评测进度在后台归并；需要人裁决的事项才进入待处理列表。

**从实践到可用版本。** 各窗口在步骤事件里引用 `skill_id` 或 harness 标识、实际加载版本、任务及验证证据。RSI 汇总反复出现的失败、人工纠正和跨工具复验，定位到一个父版本上的一项改动。候选卡说明改了什么、在哪些样例改善或退化、哪些工具已验证。固定评估器、权限与数据边界，在相同轨迹上比较候选和父版，随后通过保留集验证。用户采纳后写入 mylib Git 并发布不可变版本，保留回退到上一版本的入口。 [本库 RSI 门控协议](../../skills/skill-rsi/references/PROTOCOL.md)

**从发布到窗口采用。** 新任务可按兼容策略解析已发布版本，启动时固定版本并上报实际加载回执。文本 skill 由适配器按需读取；涉及工具配置或进程生命周期的 harness 由对应宿主在支持的加载点应用，必要时安排下一次启动。驾驶舱分别显示「有新版」「已加载」「待重启」或「不兼容」。在途任务继续使用其固定版本，回退同样记录实际生效的窗口及时间。

**任何发往具体窗口的反馈都逐次确认。** 用户点「反馈到窗口」后，从同一任务的执行记录中选择目标；确认页显示任务、机器、窗口标题、Coding 工具、执行身份和完整正文或版本变更。用户可编辑、取消或确认发送。发送时重新核对目标会话代次及授权，确认只绑定该目标、该内容和一次请求。窗口已换工具、任务已交接或内容有变时，保留草稿并重新选择确认。回执区分已提交、目标已接收及实际加载；结果未知时先核对原请求。并行验证者分别选择确认。总管和 RSI 可生成建议，只有用户确认的请求能够触发源端投递。

试点验收用一个任务关联两个不同工具的同名窗口。从失败证据生成一个候选，验证后发布；检查新任务能读取指定版本、在途任务版本仍固定。分别演练取消发送、确认前目标重建、重复点击和回执丢失。核对取消及目标失效时投递数为零、同一请求最多投递一次，并能追溯每个窗口实际使用的版本。

## SQLite 试点

采用中转服务器本地磁盘上的 SQLite。多台电脑通过同一个服务发请求，服务将存储写操作排队，事务保持短小。MCP 查询按页读取，模型请求和厂商调用在事务外执行。单实例服务可以使用 WAL，版本须包含 SQLite 官方 WAL-reset 修复；安装环境仍用受影响版本时，试点先使用回滚日志模式。生产启动时核对服务进程实际加载的 SQLite。 [SQLite 适用范围](https://sqlite.org/whentouse.html) · [WAL 与版本边界](https://sqlite.org/wal.html#the_wal_reset_bug)

| 表 | 内容和换库需保留的数据 |
| --- | --- |
| `task_attempts` | 将任务关联到各次执行、机器、工具、会话、计费账号和角色。记录接手来源或所验证的工件，以及结论证据。所有活跃任务的执行关系与未裁决结果随热库迁移 |
| `task_events` | 关键步骤与证据索引，按项目、会话、序号分页。热库保留最近 7 天和待处理任务引用的记录 |
| `wiki_entry_versions` | 按项目、记录 ID、版本和内容摘要保存可分享正文、来源及证据引用。换库保留有效版本、分歧及撤回状态，历史版本按代次检索；长期有效的决策记录独立于短期事件的保留期限 |
| `event_receipts` | 授权范围、项目、来源、事件 ID、内容摘要、序号和回执。起测保留最近 35 天的紧凑记录 |
| `quota_refresh_jobs` | 与事件关联的查询待办、重试次数和租约。全部未结案项和有效引用带入新库 |
| `quota_snapshots` | 用量快照与事件关联，热库保留近期历史。按账号及额度池索引 |
| `task_current`、`quota_current` | 活跃任务、近期结束任务和各额度池的最新事实及证据指针。结束超过 30 天且无待处理引用的任务摘要转归档 |

序号跨轮换继续递增，关联可定位到热库或归档代次。本地自动补交起测期限 14 天，早于这个期限的未确认项进入待核对列表，可以用既有回执或归档查证。35 天回执窗口覆盖 14 天补交期限。文件大小、WAL、事件日增量、待办最老年龄、写队列等待时间和 `SQLITE_BUSY` 次数作为试点监测项。需要两台服务同时写、需要高可用，或持续写队列达不到验收目标时，评估迁移 PostgreSQL。多台客户端本身仍共享当前服务入口。

### 备份和换新库

起测按 **30 天或整理后的热库达到 256 MiB** 触发轮换评估。WAL 单独增长时先检查长读事务和 checkpoint。日常备份及归档有独立空间预算，起测保留最近 7 份日备，封存库滚动保留 180 天，再按实测与项目保留要求调整。另保留经过评测的可共享经验作为 mylib 版本工件。 [SQLite WAL 文件管理](https://sqlite.org/wal.html#avoiding_excessively_large_wal_files) · [SQLite 在线备份 API](https://sqlite.org/backup.html)

1. 日常运行用 SQLite Backup API 生成一致快照；先写临时文件，做 `integrity_check`，记录 SHA-256、库代次、模式版本和最后确认序号。把可恢复副本放到独立存储并演练恢复。轮换时在短暂写入围栏内停额度领取并收尾正在提交的事务，Hook 继续本地排队。对最终一致状态做验收并封存旧库。
2. 建立新库并迁入最新状态、未完成任务和额度待办、近期事件、仍有效的幂等回执以及归档定位信息。核对最后确认序号、待办与回执计数、各账号当前额度和重置时间。新库通过检查后才原子切换服务使用的库路径，再恢复受理。
3. 保留封存库只读。新库接受写入前，可切回原库；接受后若要回退，先核对并补齐新库已经确认的事件与用量，再做受控切换。归档旧库按检索权限与保留期限清理，每次换库都验证断电恢复和已确认事件连续性。

| **额度查询防循环**。只有开发步骤入库才产生额度任务。采集器写回、驾驶舱读取、心跳、重试回执和服务内部 MCP 调用均有独立事件类型及来源标识。 | 连续写入一个步骤、十次重复投递和一次用量结果，只有一个逻辑刷新任务。限流重试沿用同一任务。 |
| **额度归属与使用建议**。记录采集时的账号绑定版本、额度池、周期及数据时效。比较任务可用的模型、短周期和周限制。帐号切换或网页登录身份无法核实时，将该次结果标为待核对。 | 周余量充足但短周期耗尽的账号显示最早可用时间；两个窗口共享订阅只计一次；一次额度下降不能直接归因于刚完成的步骤。 |
| **备份后的确认事件**。由项目所有者确定可接受的数据损失窗口和恢复时长。按此决定异机持久日志，或客户端已确认事件的可重放保留期。归档与热库重叠的记录按 `event_id` 去重。轮换前检查同时容纳活跃库、归档、新库及临时 WAL 的磁盘余量。 | 从昨晚的备份恢复，补齐备份后已确认的事件和额度任务，再重复投递。校验无漏项、无重复；磁盘不足时保持现役库可用并提示。 |
| **跨工具经验的适用与撤回**。候选经验记录仓库版本、工具版本、适用条件、反例和验证人。原始证据按项目授权；经采纳的经验单独确定共享范围。经验撤回后，检索和摘要失效对应引用。 | 一个项目中的成功做法在另一工具回放失败时保留反例；撤回后，新会话停止推荐，旧记录仍能说明当时使用了哪个版本。 |

两个需随规模实测的边界：多个活跃任务在 7 天内已超过热库容量目标时，调整保留策略或存储容量；后台额度源持续限流时，观测队列年龄并向驾驶舱暴露数据延迟。30 天和 256 MiB 均为轮换评估起点。

### 实施步骤

1. 定稿 `report_step`、任务绑定、接手、验证登记和额度回执契约。在隔离实例测试同机换工具、跨机缺少补丁、同时接手、旧执行迟到回执，以及两验证者在相同和不同基线上的相反结论。核对任务归属、额度归属、证据定位、权限隔离和崩溃恢复。
2. 用两台授权测试机接入 Codex 与 Claude Code，登记 Grok 的实际 Hook 和账号查询能力。验收每条确认事件都有在它之后触发的查询或明确失败状态，核对一条真实周余量和重置时间，再接入全局驾驶舱。
3. 演练备份、换库和可追溯经验回流。失败的候选留在评测账本；有效的候选在另一工具复验后进入 mylib。 [本库门控协议](../../skills/skill-rsi/references/PROTOCOL.md)

### 本轮本机演练

用 Python 自带 SQLite 3.50.4 在临时目录演练 200 条合成事件、单连接 WAL 写入、在线备份及新库恢复。备份和新库完整性检查均为 `ok`。新库仅带入 21 条事件明细，保留了旧回执、待查额度任务和最新额度；重试返回原序号，新事件可继续写入。该演练未覆盖真实账号、MCP 联通或服务级并发，部署环境须单独跑当前 SQLite 版本门槛及并发恢复验收。
