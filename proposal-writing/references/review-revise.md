# 申报书评审与修订适配

本路线用于已有申报书草稿的多角色审查、仲裁和迭代修订。先读本文件，再按需读取 [review-grant](../skills/review-grant/SKILL.md) 和 [peer-review](../skills/peer-review/SKILL.md)。两个上游目录保存固定版本原文；本文件负责把海外 grant/paper review 范式收束到国内申报书。

## 适用边界

- 适用：用户已经提供当年指南、模板、草稿、附件或评审意见，要求检查断点、补证、修订、降模板化表达、形成可追踪修改台账。
- 不适用：没有指南和模板却要求判断正式合规；没有证据却要求补齐预算、单位承诺、样本量、知识产权、测试场景或合作条件；要求预测获批概率、替代评审专家或给官方分数。
- 申报书材料属于项目资料。使用本模块时按用户授权处理本地文件，不套用期刊投稿的编辑部授权流程；如用户要求审查未授权的第三方 confidential material，再按 `peer-review` 的授权边界处理。

## 角色框架

借用 `review-grant` 的六角色思路，但按国内指南改写职责：

1. 写作与格式合规：模板栏目、字数、术语、定义、行文专业度。
2. 内部一致性：目标、任务、技术路线、成果、指标、预算、进度、团队职责是否对应。
3. 指南匹配与重大方向对标：只依据已提供指南、规划、重大项目材料；不新增海外 sponsor gate。
4. 科学问题、创新与方法可行性：关键科学问题是否凝练，创新点是否逐一回应问题，AI 作用是否落到数据、模型、流程或验证任务。
5. 经费、里程碑、团队与支撑条件：金额、设备、人员、合作、示范场景和历史基础是否有证据。
6. 对抗仲裁：合并前五类意见，剔除重复和经来源核查后的误报，区分必须修订、可选增强和外部补证。

第六角色不得输出“资助/不资助”“获批概率”或官方评分。可输出“提交前风险等级”和“优先修订顺序”，并说明依据。

电网/能源项目的领域检查使用 [电网评审适配](power-grid-review.md)，给既有角色按需加载能力卡和适用来源，不另建一套通用评审。需要核对意见引用的批次、阶段及标准正文状态时，使用 `scripts/validate_review_basis.py`；格式见 [依据记录](review-basis-schema.md)。用户明确要求数字评分时，可标注内部评分并公开自定维度和理由，不称官方分数；文本质量和申报材料状态分别报告，条件缺口不能被总分抵消。

## 审查输出

每条意见必须包含：

- `project_id`：项目或文件标识。
- `location`：Word 标题、章节、表格、页码、段落号或原文短引；没有定位则退回补定位。
- `quote`：足以定位的原句或摘要，避免大段复制。
- `issue_type`：`defect`、`optional_method_suggestion`、`external_evidence_gap`、`style_term`、`template_compliance`。
- `basis`：指南/模板/材料编号及位置，或“同文内 A 与 B 冲突”。不能只写“评审认为”。
- `suggestion`：可执行修改建议。
- `severity`：`critical`、`major`、`minor`。

仲裁时先核来源，再合并同义项。对已经由指南、模板或附件支持的内容，标为误报并移出修订清单；对样本、预算、IP、测试许可、合作单位、数据授权等外部条件，不得仅因草稿措辞变顺而改为已解决。

## 修订台账

建议使用 JSON 台账并运行 `scripts/validate_revision_ledger.py`。每条记录字段：

```json
{
  "id": "R01",
  "project_id": "068",
  "location": "第2章 任务1",
  "quote": "原文短引或定位摘要",
  "basis": "S02:P68；S04:第2章",
  "issue_type": "external_evidence_gap",
  "severity": "critical",
  "suggestion": "补充验证场景和责任方",
  "status": "needs_external_evidence",
  "resolved_text": "修订后的正文短摘，未解决时留空",
  "evidence": ["S02:P68"],
  "notes": "缺少现场测试许可"
}
```

`status` 只能为：

- `resolved_text`：已用正文修订解决，且不依赖外部未到位材料。
- `needs_external_evidence`：需要用户、单位、合作方或真实数据补证。
- `partial`：正文已有改进，但仍缺证据、指标或附件。
- `rejected`：经材料核查为误报、不适用或与指南冲突；须在 `notes` 写明拒绝理由。

占位、空泛承诺、未知金额、未知 IP、未知样本授权、未知现场许可、未知合作单位确认，不能作为 `resolved_text` 的证据。正文必须保留【待补】或在台账中标 `needs_external_evidence` / `partial`。

## 可借用的本地工具

`peer-review` 的工具适合结构化检查，不替代人工评审：

- `scripts/validate_claim_evidence.py`：可用于“主张—证据”矩阵，检查有无证据 ID、支持程度和对齐问题。
- `scripts/lint_review.py`：可用于带固定字段的评审意见草稿，检查占位和行动建议是否缺失；不要把其 author/editor 结构原样写进国内申报书。
- `scripts/audit_statistics_reproducibility.py`：仅当项目包含统计或实验复现实质内容时，按本项目证据改写后使用。

不要为了通过 intake validator 伪造 `READY_FOR_LOCAL_REVIEW`。申报书本地审查不需要冒充期刊审稿流程；如确需使用上游 intake，只能如实填写授权、AI 使用和保留策略。

## 修订行文

- 用专业中文申报书语体：直接陈述对象、问题、方法、指标和验证条件，减少“打造、赋能、引领、全方位、闭环体系、显著提升”等空泛套话。
- 术语保持项目内一致，例如“主配微协同”“配网灾后重构”“带电检测报告解析”“本体约束知识图谱问答”等，不在同一概念上频繁换词。
- AI 价值要落到任务：数据治理、特征抽取、知识约束、推理链校核、策略生成、仿真回放、人机确认、指标评测；不能只写“引入大模型提升智能化水平”。
- 科学问题、创新点、关键技术和考核指标逐项映射；创新点不能脱离关键科学问题另起一套口号。
- 表述强度与证据成比例。已有成果写“已形成/已完成/已应用”需材料编号；计划工作写“拟”；外部条件未落实写【待补】。
- 可降低模板化和机械重复，但不得承诺“通过 AI 检测”“无 AI 痕迹”或用规避检测作为质量目标。
